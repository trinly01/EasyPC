# Data Model — Field Specification

Field types use Directus terminology. Unless noted, every collection gets the standard system fields (`date_created`, `date_updated`, `user_created`, `user_updated`).

Select option keys are `snake_case`; display labels follow the paper form's wording.

## Naming convention

- **Every artifact we create in Directus is prefixed `easypc_`**: collections, M2M junctions, flows, roles, dashboards, presets. This keeps EasyPC schema cleanly separated from `directus_*` system tables and any future apps on the same instance.
- Field names *inside* `easypc_*` collections are not prefixed — they're already scoped.
- System collections (`directus_users`, `directus_files`) are referenced as-is, never renamed. One prefixed extension exists: `directus_users.easypc_store` (M2O → `easypc_stores`) assigns staff a branch for multi-branch filtering.

### App layout — groups & tabs

The work-order form is long, so the detail page is organized as **tabs**. `work_order_number` and `status` stay at top level (always visible above the tabs). One `group-tabs` field `grp_tabs` holds one child group per tab — group fields are `alias` type (no DB column).

Requires Directus **≥ 11.17.1** (native `group-tabs`). On older versions: install `directus-extension-group-tabs-interface`, or fall back to `group-accordion` with the same groups.

| Tab (child group of `grp_tabs`) | Interface | Fields inside, in order |
|---------------------|-----------|--------------------------|
| `grp_intake` | `group-raw` | `job_order_no`, `odoo_ticket`, `store`, `date_time_in`, `intake_path`, `customer`, `received_by`, `warranty_claim_of`, `tracking_token`, `video_call_link`, `print` |
| `grp_unit` | `group-raw` | `unit_type`, `unit_brand_model`, `password_handling`, `customer_concern`, `services`, `terms_accepted`, `terms_accepted_at`, `terms_version` |
| `grp_parts` | `group-raw` | `cpu_socket_pins_photographed`, `photo_count`, `parts` (O2M list), `files` |
| `grp_assessment` | `group-raw` | `diagnostics` (O2M list), `diagnosis_findings`, `recommended_solution`, `additional_findings`, `assessed_by`, `assessed_at`, `approvals` (O2M list) |
| `grp_work` | `group-raw` | `processes` (O2M list), `parts_used` (O2M list) |
| `grp_releasing` | `group-raw` | `test_result`, `test_remarks`, `so_number`, `amount`, `old_parts_disposition`, `released_by`, `released_at`, `receiver_name`, `receiver_id`, `service_warranty_until` |
| `grp_updates` | `group-raw` | `updates` (O2M list with `notify_customer` toggle) |

Tab order follows the service journey left→right: Intake → Unit → Parts → Assessment → Work → Releasing → Updates. Role permissions can hide tabs a role shouldn't touch (e.g. Releasing read-only for technicians).

## `easypc_work_order_parts_used` — replacement parts & additional items line items

Transactional rows for any part/item installed or charged during service. **Every row is self-contained transaction data — it stores the price at that time.** Two entry paths, both end at the same saved row:

1. **From lookup** — pick a `catalog_item` → `description`, `unit_price`, `warranty_days` auto-copy from `easypc_parts_catalog` (still editable on the row for discounts/adjustments); `price_source = catalog`
2. **Manual** — `catalog_item` left empty → staff types `description` + `unit_price` directly; `price_source = manual`. For anything not worth cataloguing (one-off parts, consumables, misc items)

Later catalog price changes never touch existing rows. Parts/items added *after* initial approval link to the `easypc_approvals` row that authorized them (T&C clause 1: extra work/cost needs written OK).

| Field | Type | Interface | Notes |
|-------|------|-----------|-------|
| `id` | UUID | — | PK |
| `work_order` | M2O | — | → `easypc_work_orders` |
| `catalog_item` | M2O | Select | → `easypc_parts_catalog`, nullable — empty = manual entry |
| `price_source` | String | Dropdown | `catalog` / `manual` — provenance of `unit_price`; auto-set by entry path, keeps pricing auditable |
| `part_type` | String | Dropdown | Same keys as `easypc_work_order_parts.part_type` — `case_other` for non-part items |
| `description` | String | Input | What was charged — copied from catalog on pick, or typed manually |
| `qty` | Integer | Input | Default 1. Line total = `qty × unit_price` |
| `unit_price` | Decimal(10,2) | Input | **The price at that time** — copied from catalog or typed; editable per line; never synced back |
| `source` | String | Dropdown | `easypc` / `customer_supplied` — customer-supplied parts price out at 0 (T&C clause 5) |
| `approval` | M2O | Select | → `easypc_approvals`, nullable — the approval that authorized this line |
| `warranty_provider` | String | Dropdown | `easypc` / `seller` / `none` — `seller` for customer-supplied parts |
| `warranty_days` | Integer | Input | Defaults from catalog item; 0 for customer-supplied |
| `warranty_until` | Date | Date | Set by Flow at release = `released_at + warranty_days`; queryable for active warranties |
| `notes` | String | Input | e.g. which intake part it replaced |
| `sort` | Integer | — | |

## `easypc_work_orders_services` — M2M junction for `services`

Auto-created as the junction, then extended with transaction fields. This is the **price snapshot**: each row records what the service cost *on this work order*, so later price changes in `easypc_services` never rewrite history.

| Field | Type | Notes |
|-------|------|-------|
| `id` | Integer | PK |
| `easypc_work_orders_id` | M2O | → `easypc_work_orders` |
| `easypc_services_id` | M2O | → `easypc_services` |
| `charged_price` | Decimal(10,2) | Copied from `easypc_services.price` when the row is created (Flow or app default); editable per work order for discounts/adjustments; **never synced back** to the lookup |

> The sum of `charged_price` across rows is the expected service total — a Flow can use it to pre-fill `amount` at release, or to flag when `so_number`'s amount differs.

## `easypc_settings` — singleton

One-row settings record — centrally managed legal text and shop policy values, referenced by prints, emails, flows, and the tracker instead of hardcoding.

| Field | Type | Notes |
|-------|------|-------|
| `id` | UUID | PK |
| `terms_version` | String | e.g. `EPC-TC-2026-01` — snapshot into `work_orders.terms_version` at intake |
| `terms_conditions` | Text (HTML) | Full T&C — single source for tracker page, emails, reprints |
| `liability_waiver` | Text (HTML) | Waiver text printed on the service form |
| `service_warranty_days` | Integer | Labor warranty (30). `easypc_warranty_stamp` currently hardcodes 30 — migrate the flow to read this |
| `part_warranty_default_days` | Integer | Fallback when a catalog part lacks `warranty_days` (90) |
| `unclaimed_days` | Integer | Claim window before `unclaimed` (30, T&C clause 6) — for `easypc_unclaimed_reminder` |
| `tracking_url` | String | Public tracker base URL for printed forms |
| `video_base_url` | String | `https://meet.jit.si` — swap for self-hosted Jitsi later |
| `support_email` / `support_phone` | String | Contact details for tracker/emails |

Access: read for all three EasyPC roles; update restricted to `easypc_manager`.

> **Print caveat:** the `print` field only expands the work order (`*.*.*`) — the template can't reach the singleton. That's why `terms_version` is *snapshotted* onto the WO at intake: the printed form shows the version the customer actually agreed to, while the singleton feeds live surfaces (tracker, emails, admin).
